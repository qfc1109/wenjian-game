# 问剑江湖后续开发路线文档

## 1. 文档定位

本文档作为《问剑江湖》后续开发的主方向文档。以后继续开发时，优先以本文档为路线参考，再结合 `task_plan.md`、`progress.md`、`findings.md` 中的最新执行记录推进。

当前项目已经完成整体架构规划、协议与配置最小骨架、后端 Maven 最小模块、WebSocket 登录/进入区域/单技能/秘境结算的文本调试链路，以及第二轮可执行美术标准。

下一阶段目标不是一次性复制成熟商业服的完整复杂度，而是先做出一个可运行、可联调、可扩展的“服务端权威战斗竖切版本”。

## 2. 当前项目状态

### 2.1 已完成内容

- 单仓库目录结构：`wenjian-game-server/`、`wenjian-client/`、`protobuf/`、`config/`、`docs/`。
- 后端 Maven 最小模块：`wenjian-share`、`wenjian-protobuf`、`wenjian-config`、`wenjian-game-core`、`wenjian-gateway-ws`。
- 最小 protobuf 契约：登录、进入区域、区域快照、输入帧、技能事件、伤害事件、秘境开始和结算。
- 最小 CSV 配置：玩家模板、地图、区域、技能、怪物、秘境、奖励池、道具。
- WebSocket 临时文本链路：
  - `LOGIN`
  - `ENTER_REGION`
  - `SKILL`
  - `START_ROGUE`
  - `FINISH_ROGUE`
- Unity `Proto_CombatField` 原型壳说明。
- 第二轮可执行美术标准：明快清爽像素武侠、战斗读得清楚、48x48 玩家、32x32 Tilemap。

### 2.2 当前核心不足

- 后端主要逻辑仍集中在 `wenjian-gateway-ws`，`wenjian-game-core`、`wenjian-config`、`wenjian-protobuf` 基本还是模块壳。
- 当前 WebSocket 使用文本调试协议，还没有真正使用 protobuf 生成代码和统一消息包装。
- 配置表尚未进入正式加载、校验和访问流程，服务端仍有硬编码数据。
- 还没有服务端权威 Tick、输入队列、移动校验、技能冷却、碰撞命中、伤害结算和快照广播。
- 没有账号、角色、在线上下文、持久化、断线重连和奖励写回。
- Unity 仍是原型说明，没有正式工程、场景、脚本和真实联调画面。
- KCP 实时通道还未创建，当前只有 WebSocket 低频验证链路。

## 3. 参考 longnv_server2_1 的取舍

`longnv_server2_1` 是成熟游戏服工程，可以作为工程结构参考，但不能在早期完整照搬。

### 3.1 值得借鉴

- 基础设施层与业务模块层分离。
- 类似 `foundation` 的基础能力分层：配置、网络、事件、日志、玩家上下文、持久化、远程连接。
- 业务按领域拆分，例如账号、背包、战斗、活动、GM、邮件、排行榜等。
- 配置表启动加载、运行期访问、字段映射和错误码体系。
- 协议入口统一分发，业务 Handler 不直接关心底层网络细节。
- 在线玩家上下文、断线处理、日志记录、GM 调试工具。

### 3.2 暂不照搬

- 不立即创建大量外围业务模块。
- 不立即做跨服、中心服、活动系统、商城、排行榜、支付等复杂系统。
- 不把所有玩法提前抽象成大型框架。
- 不在还没有可玩竖切前引入过多数据库表和运营后台。
- 不为了“像成熟项目”而增加当前用不到的目录和封装。

### 3.3 当前推荐原则

先借鉴 longnv 的工程边界和基础设施思想，再按《问剑江湖》的玩法节奏逐步实现。第一目标是可玩、可联调、可验证；第二目标才是模块数量和系统完整度。

## 4. 后续总路线

### 阶段一：把最小链路变成真实工程链路

目标：把当前文本调试 Demo 改造成真正依赖 protobuf、config 和 core 模块的服务链路。

核心任务：

- 为 `protobuf/` 建立 Java 生成流程，生成代码进入 `wenjian-protobuf`。
- 设计统一消息包装，替代 `LOGIN xxx` 这类文本协议。
- 在 `wenjian-config` 中实现 CSV 加载、字段解析、主键唯一校验和外键校验。
- 把玩家模板、技能、怪物、秘境、奖励池从硬编码迁移到配置访问层。
- 在 `wenjian-game-core` 中沉淀实体、坐标、区域、技能、秘境实例等核心模型。
- `wenjian-gateway-ws` 只保留网络接入、协议解析、调用 core、返回响应。

验收标准：

- `mvn test` 通过。
- 登录、进入区域、技能、秘境链路仍可跑通。
- 服务端行为来自配置和 core 服务，不再主要依赖网关内硬编码。
- 错误配置会在测试或启动校验中失败，不静默兜底。

### 阶段二：实现服务端权威战斗竖切

目标：完成一张地图、一个玩家、一个训练敌人、一个技能、一个秘境房间的可玩服务端模拟。

核心任务：

- 创建基础战斗 Tick 循环。
- 建立输入帧模型：移动方向、技能意图、客户端序号、服务端确认序号。
- 实现玩家移动校验：速度、边界、阻挡、非法输入处理。
- 实现技能释放流程：冷却、前摇、方向、范围、命中、伤害。
- 实现实体状态：生命、死亡、坐标、阵营、类型。
- 实现区域快照输出：当前 Tick、实体列表、事件列表。
- 秘境实例中加入怪物清理条件，不能直接 `FINISH_ROGUE` 领奖。

验收标准：

- 不依赖客户端也能用测试驱动完整 Tick。
- 技能是否命中由服务端计算。
- 怪物血量会真实变化，死亡后秘境才能结算。
- 同一套 core 能服务大世界训练区域和单人秘境。

### 阶段三：创建真实 Unity Proto_CombatField 原型

目标：客户端真正接入服务端并展示第一条可玩链路。

核心任务：

- 创建正式 Unity 原型工程。
- 使用第二轮美术标准搭建竹林战斗场景。
- 实现 8 方向移动输入、Pixel Perfect 相机、基础 HUD。
- 接入 WebSocket 登录和进入区域。
- 展示服务端 `RegionSnapshot` 中的玩家和训练敌人。
- 发送技能意图，播放服务端确认后的技能事件和受击反馈。
- 展示秘境开始和结算结果。

验收标准：

- 可以从客户端连接本地服务端。
- 玩家、敌人、技能方向、受击反馈在画面中可读。
- 客户端不决定伤害和奖励，只表现服务端结果。
- 能录屏或截图作为阶段验收材料。

### 阶段四：补齐生产基础设施

目标：让项目从“可玩原型”进入“可持续开发工程”。

核心任务：

- 账号和角色持久化。
- 在线玩家上下文和会话管理。
- 断线、重连、重复登录处理。
- 数据库初始化脚本和本地开发配置。
- 日志体系：登录日志、战斗日志、奖励日志、异常日志。
- GM 调试命令：加道具、传送、刷新怪物、进入秘境、重置角色。
- Maven Wrapper 固定 Maven 版本。
- 本地一键启动脚本和基础运维说明。

验收标准：

- 角色数据能保存和重新登录读取。
- 奖励结算能写回角色数据。
- 关键操作有日志。
- 新机器按文档能构建、测试、启动。

### 阶段五：扩展核心玩法

目标：在竖切稳定后，再扩展成完整的武侠肉鸽游戏。

推荐顺序：

1. 大世界区域：主城、竹林、野外区域、区域切换。
2. 战斗能力：多个技能、普通攻击、冲刺、受击硬直、怪物 AI。
3. 秘境肉鸽：房间节点、随机事件、怪物波次、宝箱、奖励选择。
4. 角色成长：等级、装备、技能升级、属性成长。
5. 背包和道具：获得、消耗、堆叠、使用。
6. 任务和引导：主线目标、日常目标、秘境目标。
7. 社交和外围：聊天、邮件、排行榜、活动、运营后台。

## 5. 推荐模块演进

当前不要一次性建满模块。按阶段逐步拆分：

### 5.1 当前保留

- `wenjian-gateway-ws`
- `wenjian-game-core`
- `wenjian-config`
- `wenjian-protobuf`
- `wenjian-share`

### 5.2 下一批优先新增

- `wenjian-battle`：当战斗 Tick、技能、伤害开始变复杂时拆出。
- `wenjian-world`：当区域管理、AOI、怪物刷新、PK 规则开始变复杂时拆出。
- `wenjian-rogue`：当秘境生成、房间、事件和奖励选择开始变复杂时拆出。

### 5.3 后续再新增

- `wenjian-gateway-kcp`：当 Unity 原型已经证明 WebSocket 链路后，再做实时通道。
- `wenjian-admin`：当账号、角色、GM、日志稳定后再做后台。
- `wenjian-ops` 或脚本目录：当需要部署、打包、环境管理时再补。

### 6.2 第二优先级

### 6.3 第三优先级

- 验证画面读得清楚、操作延迟可接受、坐标尺度合理。
- 根据 Unity 反馈调整 Tick、坐标、技能范围和协议字段。

## 7. 开发纪律

- 每次只做一个可验收闭环，不同时铺太多模块。
- 优先写测试或验收脚本，再实现最小可用功能。
- 不写无依据兜底，不用默认假数据掩盖配置错误。
- 协议字段发布后不复用，删除字段必须 `reserved`。
- 配置主键、外键、必填字段必须可校验。
- 网关只负责接入和转发，核心规则下沉到 core/battle/world/rogue。
- 客户端只上传意图，不上传最终结果。
- 服务端决定命中、伤害、死亡、掉落和奖励。
- 文档和代码不一致时，以可运行测试和最新任务记录为准，并及时修正文档。

## 8. 下次继续开发建议

下次继续开发时，建议从“阶段一：把最小链路变成真实工程链路”开始，第一项任务是：

> 建立 protobuf Java 生成流程，并让 `wenjian-gateway-ws` 的登录、进入区域、技能、秘境链路开始使用生成后的协议类型。

推荐验收命令：

```powershell
$env:JAVA_HOME='E:\JAVA\jdk21'
$env:MAVEN_HOME='E:\apache-maven-3.9.16'
$env:Path="$env:JAVA_HOME\bin;$env:MAVEN_HOME\bin;$env:Path"
cd E:\qfc\workspace\wenjian-game\wenjian-game-server
mvn -q test
```

如果 protobuf 生成流程尚未接入 Maven，可以先用独立脚本生成，再在 Maven 中固化；但最终目标必须是新机器可以按文档稳定生成和构建。

## 9. 阶段目标一句话

《问剑江湖》的近期方向是：先做出一个服务端权威、Unity 可联调、配置和协议真实生效的小型武侠动作肉鸽竖切版本，再逐步扩展成完整江湖。
