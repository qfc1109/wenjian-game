# 问剑江湖项目目录与整体架构设计

## 1. 文档目标

本文档用于固化《问剑江湖》第一阶段的项目目录、系统边界、后端模块职责、客户端协作边界、网络协议分层、配置表体系和后续实施顺序。

当前阶段只确认整体架构和目录设计，不创建 Java 后端多模块工程、Unity 客户端工程、协议生成流程或配置导出脚本。具体工程骨架将在本设计确认后分阶段创建。

## 2. 项目定位

《问剑江湖》是一款像素风、俯视角即时动作、武侠肉鸽游戏。游戏采用“同一个服务器 = 同一个江湖世界”的服务器模型，玩家创建的角色默认进入同一个大世界。

第一版重点是建立可扩展的服务器权威架构，支持区域式大地图、城镇安全区、野外 PK、单人秘境实例、服务端权威战斗 Tick，以及后续服务器后台管理能力。

## 3. 第一版架构边界

第一版采用“区域式大地图 + 单人秘境实例”的结构。

大世界负责玩家日常移动、城镇活动、野外探索、NPC 交互、区域广播和 PK 规则。秘境负责单人肉鸽战斗流程，包括秘境生成、怪物刷新、奖励池、战斗结算和局外成长衔接。

实时模型采用服务端全权威。客户端负责输入采集、表现预测、动画表现、特效播放和 UI 展示；服务端负责状态判定、移动校验、技能命中、伤害结算、死亡复活、掉落奖励和最终同步。

## 4. 推荐一级目录

```text
wenjian-game/
├─ wenjian-game-server/   # Java 后端多模块项目
├─ wenjian-client/        # Unity 客户端与像素美术素材
├─ protobuf/              # 前后端 protobuf 协议源文件
├─ config/                # CSV/XLSX 配置表与导出脚本
└─ docs/                  # 项目设计文档、实施计划和决策记录
```

### 4.1 wenjian-game-server

后端服务端工程目录，后续用于承载 Java 多模块项目。第一版建议先保持单仓库、多模块结构，避免在项目早期拆分多个仓库造成协议、配置和部署协作成本过高。

### 4.2 wenjian-client

Unity 客户端工程目录，后续用于承载像素风客户端工程、美术资源、动画控制、特效资源、输入同步、网络接入和 UI 表现。

客户端不是后端附属模块。它需要单独进行视觉方向确认，包括主视角、角色比例、动作节奏、技能特效、场景氛围、UI 结构和资源规格。该部分应在正式创建 Unity 工程前补充视觉方案与效果图。

### 4.3 protobuf

协议源文件目录，用于存放前后端共享的 `.proto` 文件。协议源文件应独立于后端生成代码目录，便于 Unity 客户端、Java 后端和后续工具链共同消费。

### 4.4 config

配置表源文件与导出工具目录。第一版建议以 CSV 或 XLSX 作为策划可编辑源，导出为服务端和客户端各自可加载的结构化数据。

### 4.5 docs

项目文档目录，用于保存架构设计、阶段计划、协议说明、配置表规范、客户端视觉方案、服务器运维说明和决策记录。

## 5. 后端模块设计

后端建议采用 Java 多模块结构。模块边界优先按业务职责划分，公共能力下沉到共享模块，实时同步和普通业务请求分离。

```text
wenjian-game-server/
├─ wenjian-gateway-ws
├─ wenjian-gateway-kcp
├─ wenjian-game-core
├─ wenjian-world
├─ wenjian-rogue
├─ wenjian-battle
├─ wenjian-config
├─ wenjian-protobuf3
├─ wenjian-share
└─ wenjian-admin
```

### 5.1 wenjian-gateway-ws

负责 WebSocket 长连接、登录后的业务请求、服务端主动推送和低频状态同步。

适合承载账号登录、角色列表、角色创建、背包变化、任务状态、聊天、邮件、商城、活动、系统通知等非高频协议。

### 5.2 wenjian-gateway-kcp

负责 KCP 实时通道，处理高频输入、移动同步、战斗操作、区域状态快照和秘境战斗同步。

该模块只负责网络接入、连接管理、协议收发和转发，不直接实现复杂战斗规则。战斗规则应下沉到 `wenjian-battle`，区域规则应下沉到 `wenjian-world`。

### 5.3 wenjian-game-core

负责账号、角色、背包、任务、成长、货币、装备、技能养成等核心持久化玩法。

该模块提供角色基础数据和局外成长能力，是大世界、秘境、战斗结算共同依赖的核心业务层。

### 5.4 wenjian-world

负责大世界区域、地图、NPC、怪物分布、玩家进入离开区域、区域广播、PK 规则、安全区和新手保护区。

第一版采用区域式地图，不追求无缝大世界。区域可以按地图编号、场景实例编号和区域坐标进行管理。城镇区域默认安全，野外区域允许 PK，新手区和保护区可通过配置限制 PK。

### 5.5 wenjian-rogue

负责肉鸽局外规则、秘境生成、关卡节点、房间类型、奖励池、事件选择和秘境结算。

第一版秘境为单人实例。秘境内的战斗仍由服务端权威模拟，客户端只上传操作输入并播放服务端确认后的表现。

### 5.6 wenjian-battle

负责服务端权威战斗 Tick，包括实体状态、技能释放、碰撞/命中判定、伤害结算、Buff、死亡、掉落触发和战斗快照输出。

该模块应尽量保持和网络层解耦。输入来自大世界或秘境，输出为权威状态变化和快照，由网关模块负责发送给客户端。

### 5.7 wenjian-config

负责 Java 侧配置表映射、加载、校验和访问接口。

配置表应在服务启动时进行完整校验。缺失关键字段、重复主键、非法引用和数值越界应直接阻止启动，避免运行期静默兜底。

### 5.8 wenjian-protobuf3

负责 Java protobuf 生成代码。该模块不手写业务逻辑，只承载由 `protobuf/` 源文件生成的 Java 类型。

### 5.9 wenjian-share

负责公共错误码、事件定义、基础模型、时间工具、坐标类型、通用常量和跨模块共享接口。

该模块应保持轻量，避免把具体玩法规则塞进公共层，防止共享模块逐渐变成无边界的大杂烩。

### 5.10 wenjian-admin

负责后期服务器控制后台，包括玩家查询、角色封禁、邮件发放、配置热更新控制、服务器状态查看、区域状态查看和运营工具。

第一版可以只预留模块，不急于实现后台功能。涉及权限、审计和高风险操作时，需要单独设计。

## 6. 客户端方向与协作边界

客户端第一阶段不应只等待后端完成后再启动。像素动作游戏的手感、角色比例和技能表现会反过来影响战斗 Tick、碰撞尺寸、技能前后摇、同步频率和协议字段。

因此，客户端应单独补充以下设计内容：

- 视觉基准：俯视角比例、角色尺寸、地图格子或自由坐标、主城/野外/秘境的画面风格。
- 角色动作：待机、移动、普攻、受击、闪避、冲刺、技能释放、死亡、复活。
- 技能表现：剑气、突进、圆形斩击、扇形攻击、落点预警、残影和命中特效。
- UI 结构：登录、创角、主界面、背包、角色、技能、任务、秘境选择、战斗 HUD。
- 资源规格：像素角色帧尺寸、动画帧率、特效尺寸、地图切片规格、图集命名规范。

这些内容建议在后续形成独立文档与效果图方案，再决定是否创建 Unity 工程骨架和资源目录。

## 7. 网络协议分层

第一版网络方案为 WebSocket + KCP。

WebSocket 负责低频业务和可靠推送，KCP 负责实时输入和高频状态同步。两条通道共享登录态和角色身份，但协议用途保持清晰分离。

### 7.1 WebSocket 协议范围

- 登录态确认与角色进入游戏。
- 账号、角色、背包、任务、成长等普通业务请求。
- 聊天、邮件、系统通知和活动信息。
- 非高频状态推送。
- KCP 通道建立所需的令牌、地址和会话信息。

### 7.2 KCP 协议范围

- 玩家输入帧。
- 移动方向、位移意图、技能释放意图。
- 区域状态快照。
- 战斗实体状态同步。
- 关键战斗事件确认。

### 7.3 协议设计原则

- 客户端上报意图，不上报最终结果。
- 服务端计算权威状态，再广播或回包。
- 高频协议保持轻量，避免携带背包、任务等低频业务数据。
- 协议字段必须有明确含义，不编写猜测性兼容字段。
- 关键操作需要服务端校验角色状态、区域规则、技能冷却和目标合法性。

## 8. 服务端权威战斗模型

战斗采用固定 Tick 或准固定 Tick 推进。客户端发送输入，服务端按 Tick 处理输入队列，计算移动、技能、命中、伤害和状态变化，再输出快照或事件。

客户端可以做表现层预测，例如移动预表现、技能前摇播放和镜头反馈，但不能决定命中、伤害、掉落或奖励。

第一版应优先保证规则清晰和调试便利，不急于实现复杂回滚。若后续对操作手感要求提高，可在客户端预测和服务端校正之间逐步增强。

## 9. 世界与实例模型

### 9.1 大世界区域

大世界按区域管理，每个区域有独立地图配置、出生点、NPC、怪物刷新点、安全区规则和 PK 规则。

玩家进入区域后，由区域服务管理玩家集合、实体集合、区域广播和状态同步。玩家跨区域时，服务端完成角色状态保存、离开旧区域、进入新区域和初始快照下发。

### 9.2 安全区与 PK

城镇和主城默认安全，玩家不能互相攻击。野外区域允许玩家互相攻击。新手区和保护区通过配置限制 PK。

PK 规则应由服务端根据区域配置和角色状态判定，客户端只负责展示是否可攻击、目标提示和操作反馈。

### 9.3 单人秘境实例

秘境为单人实例。玩家进入秘境后，服务端创建独立秘境上下文，加载秘境生成结果、怪物波次、房间事件和奖励池。

秘境结束时，服务端结算奖励并写回角色成长数据。客户端展示结算动画和奖励结果，但不参与奖励判定。

## 10. 配置表体系

配置表用于承载地图、区域、怪物、技能、Buff、掉落、秘境、奖励、任务、装备和成长曲线。

推荐源文件放在 `config/`，后续可按领域拆分：

```text
config/
├─ source/        # CSV/XLSX 源表
├─ schema/        # 字段定义与校验规则
├─ export/        # 导出后的服务端/客户端配置
└─ tools/         # 导出、校验和差异检查脚本
```

配置表设计原则：

- 每张表有稳定主键。
- 外键引用必须可校验。
- 服务端和客户端共享的配置从同一份源表导出。
- 服务端启动时校验关键配置。
- 不使用默认假数据掩盖配置错误。
- 配置热更新属于后续能力，第一版不作为必要功能。

## 11. Protobuf 目录建议

协议源文件建议按职责拆分：

```text
protobuf/
├─ common/        # 通用类型、错误码、坐标、时间戳
├─ account/       # 登录、账号、角色选择
├─ core/          # 背包、任务、成长、装备
├─ world/         # 大世界、区域、NPC、PK
├─ rogue/         # 秘境、肉鸽事件、奖励
└─ battle/        # 输入帧、战斗事件、状态快照
```

协议文件应先服务于真实调用链。不要为了预留未来功能提前定义大量暂不用字段。

## 12. 后续实施顺序

建议按以下顺序推进：

1. 确认本文档中的目录结构、模块职责、网络分层和配置表方向。
2. 补充客户端视觉方向文档与效果图，包括角色、场景、技能特效和 UI 氛围。
3. 拆分第一阶段实施计划，明确后端骨架、协议骨架、配置表骨架、客户端原型的创建顺序。
4. 创建项目一级目录和占位说明。
5. 创建 Java 后端多模块骨架。
6. 创建 protobuf 协议初始结构。
7. 创建配置表源目录与示例表。
8. 创建 Unity 客户端原型或资源验证工程。
9. 实现最小可运行链路：登录进入区域、角色移动、服务端同步、单个技能释放、单人秘境战斗闭环。

## 13. 风险与决策点

### 13.1 技术栈细节尚未最终落地

本文档确认的是架构边界，不直接决定 Maven 或 Gradle、Java 版本、Spring 版本、KCP 库、数据库、缓存、消息队列和部署方式。

这些技术选择会影响构建配置和工程骨架，后续创建后端项目时需要单独确认。

### 13.2 前端表现会影响战斗参数

动作游戏的角色尺寸、攻击范围、技能前摇、移动速度和特效范围会影响服务端战斗 Tick 与协议设计。前端视觉和手感设计不应长期滞后。

### 13.3 管理后台需要权限设计

后台管理涉及高风险操作，后续实现前必须单独设计权限、审计、操作确认和环境隔离。

### 13.4 配置热更新不是第一版必要能力

第一版优先保证配置加载和校验可靠。热更新、灰度发布和在线修表属于后续增强。

## 14. 当前阶段结论

第一阶段建议先保留单仓库结构，将后端、客户端、协议、配置和文档放在同一个项目根目录下统一推进。

后端以 Java 多模块为核心，网络层拆分 WebSocket 与 KCP，玩法层拆分核心成长、大世界、肉鸽秘境和权威战斗。客户端需要尽快补充独立的视觉与动作方案，避免项目早期只围绕后端推进。

本文档确认后，下一步不应直接进入完整工程实现，而应先补充客户端视觉方案，再共同拆分第一阶段实施计划。
