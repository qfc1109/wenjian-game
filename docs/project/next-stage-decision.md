# 问剑江湖下一阶段项目经理决策

## 1. 背景

当前项目已完成整体架构设计，并进入“客户端视觉方向、项目骨架、协议契约和最小闭环”之间的推进取舍。

用户明确希望引入多智能体协作，并授权项目经理在普通决策上自主推进。项目经理已调度美术总监、架构师、后端高级工程师、Unity 前端工程师四个角色进行并行预研。

## 2. 各角色结论摘要

### 2.1 架构师

架构师建议最低风险路线为：

```text
目录骨架 → 协议骨架 → 后端最小权威链路 → Unity 灰盒验证 → 视觉概念细化
```

核心理由：

- 服务端全权威和 WebSocket + KCP 已确定，协议和模块边界会影响所有后续工作。
- 如果先做完整视觉，可能产生“画面成立但工程返工”的结果。
- 如果先做复杂后端，可能过早把架构做重。

### 2.2 美术总监

美术总监建议首批先生成 16 张概念图，其中第一优先级 7 张：

1. 江湖区域式大地图总览
2. 问剑城主城
3. 竹林古道
4. 藏剑地宫
5. 玩家四职业方向
6. 剑气技能特效组
7. 战斗 HUD 氛围图

核心理由：

- 先统一像素风、俯视角、武侠江湖、即时动作肉鸽的视觉基调。
- 先看气质，不把概念图直接当最终 Unity 资源。
- 角色比例、技能亮度、场景密度和 HUD 可读性会影响后续战斗和协议。

### 2.3 后端高级工程师

后端建议：

- 构建工具：Maven 3.9.x，并使用 Maven Wrapper 固定版本。
- Java：优先 Java 21 LTS。
- Spring：使用 Spring Boot 当前稳定 4.0.x 线，不使用 RC/SNAPSHOT。
- 第一阶段采用单 JVM、多模块、双通道最小链路，不拆多进程。
- 首批链路：WebSocket 登录、KCP 绑定、移动同步、单个技能、单人秘境闭环。

### 2.4 Unity 前端工程师

Unity 前端建议：

- 技术路线：Unity 当前 LTS 线 + URP 2D Renderer + Tilemap + Pixel Perfect Camera + Cinemachine + Input System + Sprite 动画。
- 第一阶段原型：`Proto_CombatField`，验证角色移动、相机、Tilemap、普攻、两个技能、HUD、网络输入占位。
- 推荐规格：主角 48x48 画布、32 PPU、32x32 地图瓦片、8 方向移动、普攻 8 帧、技能 10-12 帧。

## 3. 方案比较

### 方案 A：先生成概念美术包

核心做法：先生成第一优先级 7 张概念图，建立 `wenjian-client/ArtConcepts/`，同时记录提示词、用途和后续拆分价值。

优点：

- 能最快看到《问剑江湖》要做成什么样。
- 满足前端视觉优先的当前诉求。
- 概念图不牵涉接口、数据库、权限或构建配置，工程风险低。

缺点或风险：

- 概念图不是最终 Unity 可用资源。
- 如果没有工程约束，视觉可能偏离服务端权威战斗需求。

适用场景：

- 需要先统一美术方向、角色比例、技能氛围和 UI 气质。

修改范围：

- 新增概念素材目录、图片文件、素材清单文档。

测试或检查影响：

- 检查图片文件存在、命名规范、素材清单完整、密钥未入库。

### 方案 B：先创建目录与协议骨架

核心做法：先创建一级目录、protobuf 源文件、配置表示例和后端多模块空骨架。

优点：

- 能尽早稳定工程边界和前后端契约。
- 便于后续后端和 Unity 并行开发。

缺点或风险：

- 短期看不到视觉效果。
- 如果视觉参数尚未确定，协议字段可能需要回改。

适用场景：

- 准备进入工程骨架和网络联调。

修改范围：

- 涉及目录、协议、配置和构建骨架。属于中高风险，需要分阶段执行。

测试或检查影响：

- 需要 protobuf 编译检查、构建检查和配置表校验。

### 方案 C：直接做 Unity 灰盒原型

核心做法：先创建 Unity 工程或原型目录，做角色移动、Tilemap、普攻、技能和 HUD。

优点：

- 最快验证动作手感。
- 能直接产出影响后端协议的角色尺寸、技能形状和 Tick 需求。

缺点或风险：

- 需要 Unity 工程环境和包版本确认。
- 如果素材和协议都未定，原型容易成为孤立 Demo。

适用场景：

- 已准备好 Unity 工程初始化，并优先验证操作手感。

修改范围：

- 涉及客户端工程结构和包配置。属于高风险方案，暂不直接执行。

测试或检查影响：

- 需要 Unity Play Mode、场景截图和资源导入检查。

### 方案 D：后端最小链路优先

核心做法：直接搭建 Java 多模块、WebSocket、KCP 占位、战斗 Tick 和秘境闭环。

优点：

- 服务端全权威项目最终必须走这条路。
- 能尽早验证架构承载能力。

缺点或风险：

- 如果协议、配置和客户端表现没有同步约束，后端容易做重。
- 涉及构建配置、多模块工程和网络组件，风险较高。

适用场景：

- 目录、协议和客户端参数已经足够清楚后。

修改范围：

- 后端工程骨架和业务代码。属于高风险方案，需拆实施计划。

测试或检查影响：

- 需要 Maven 构建、单元测试、集成测试和 smoke 检查。

## 4. 项目经理推荐

推荐采用“低风险双轨推进”：

```text
第一步：生成首批概念美术包
第二步：整理客户端视觉方向文档
第三步：创建目录与协议骨架实施计划
第四步：创建目录和 protobuf/config 最小骨架
第五步：创建后端 Maven 多模块骨架
第六步：创建 Unity 灰盒原型
第七步：联调最小服务端权威链路
```

推荐理由：

- 用户当前最关心前端效果，概念美术包是最低风险、最快反馈的产物。
- 架构师提出的工程契约风险是真实存在的，所以概念图之后必须马上回到目录与协议骨架。
- 不先做完整 Unity 工程，不先做复杂后端，避免早期返工。

不推荐直接执行方案 B，是因为当前视觉参数尚未形成基础认知。

不推荐直接执行方案 C，是因为 Unity 工程初始化和资源规格尚未确认。

不推荐直接执行方案 D，是因为后端会受到前端角色尺寸、技能形状、同步频率和协议字段影响。

## 5. 已确认技术方向

后端方向：

- Maven 3.9.x，使用 Maven Wrapper 固定。
- Java 21 LTS 优先。
- Spring Boot 当前稳定 4.0.x 线。
- 单 JVM 多模块先行，不急于拆微服务或引入 RPC。

Unity 方向：

- Unity 当前 LTS 线。
- URP 2D Renderer。
- Tilemap。
- Pixel Perfect Camera。
- Cinemachine。
- Input System。
- Sprite flipbook 动画。
