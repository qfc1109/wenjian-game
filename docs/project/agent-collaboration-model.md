# 问剑江湖多智能体协作机制

## 1. 目标

本文档定义《问剑江湖》项目在 Codex 协作中的多智能体分工、决策边界、分支策略、进度记录方式和成果验收方式。

该机制的目标是让项目在用户离线时仍能持续推进，同时确保关键上下文写入仓库，避免开发记忆丢失。

## 2. 总体原则

- 始终使用中文记录项目进度、方案分析和最终总结。
- 每次修改项目文件前先检查 git 状态。
- 普通低风险决策由项目经理智能体判断并推进。
- 高风险操作不自动执行，包括合并分支、删除分支、`git reset --hard`、丢弃已有改动、推送远程仓库。
- 密钥、令牌和账号信息不得写入仓库、文档、日志或提交信息。
- 所有重要阶段输出都必须同步更新 `progress.md`。
- 所有关键发现和外部资料记录到 `findings.md`。
- 所有阶段计划、状态变化和待办事项记录到 `task_plan.md`。

## 3. 角色分工

### 3.0 主线程与子代理边界

项目内所有会改变工作区状态的操作只能由主控 Codex 会话执行。

强制规则：

- 只有主线程智能体可以修改代码、测试、项目配置、构建脚本、协议文件、配置表、Unity 场景/资源文件以及任何可能被提交的项目文件。
- 子代理智能体只允许并行读取、检索、分析、比较方案，或生成计划文档、需求文档、调研文档、检查清单等非代码内容。
- 子代理智能体不得直接修改代码或测试，不得改 `.proto`、CSV/XLSX 配置、Unity 场景、Maven 配置、脚本、资源文件或项目根部规则文件。
- 子代理智能体不得执行 `git add`、commit、push、merge、reset、revert、删除分支、删除文件或任何会改变工作区状态的命令。
- 主线程智能体可以吸收子代理产出的分析和计划，但最终文件修改、测试运行、状态检查、提交准备和总结都必须由主线程完成。

### 3.1 项目经理

项目经理由主控 Codex 会话承担。

职责：

- 维护项目总体进度。
- 拆分任务并调度其他角色智能体。
- 对多个方案进行取舍。
- 判断是否需要创建 `codex/` 前缀实验分支。
- 汇总各角色成果。
- 更新 `task_plan.md`、`progress.md` 和 `findings.md`。
- 负责最终检查、提交和总结。

### 3.2 美术总监

职责：

- 规划整体美术方向。
- 生成或组织生成概念图和素材。
- 负责世界地图、角色、主城、小镇、野外、秘境、技能特效和 UI 氛围的风格统一。
- 输出素材清单、提示词、命名规范和质量评估。
- 与 Unity 前端工程师协作，将概念图逐步拆成可落地资源规格。
- 作为子代理参与时，只输出调研、规格、清单、提示词或评审意见，不直接写入项目资源或代码。

### 3.3 架构师

职责：

- 维护项目整体技术架构。
- 分析后端、客户端、协议、配置和资源管线之间的边界。
- 对高风险方案进行评估。
- 确保新方案不破坏既有架构方向。
- 给出第一阶段到可运行闭环的路线。
- 作为子代理参与时，只输出架构分析、风险评估或计划文档，不直接修改工程文件。

### 3.4 后端高级工程师

职责：

- 负责 Java 后端多模块工程设计方案、实现建议和测试建议。
- 分析 WebSocket、KCP、服务端权威战斗、大世界区域、单人秘境和配置加载相关代码。
- 为最小可运行后端链路输出拆解计划、风险清单和验收建议。
- 作为子代理参与时，不直接修改代码、不新增测试、不运行改变工作区状态的命令；需要实现时交回主线程智能体执行。

### 3.5 Unity 前端工程师

职责：

- 负责 Unity 客户端原型规划、实现建议和验收建议。
- 分析角色移动、相机、地图表现、动画、技能特效、HUD 和网络输入占位。
- 与美术总监协作确认资源尺寸、动画帧、瓦片规格和导入规范。
- 验证客户端效果图、场景截图和基础交互的方案与标准。
- 作为子代理参与时，不直接修改 Unity 场景、脚本、资源、`.meta` 文件或测试；需要实现时交回主线程智能体执行。

## 4. 分支策略

默认开发分支为 `codex/wenjian-architecture`。

当出现多个可并行验证的方案时，可以创建 `codex/` 前缀实验分支，例如：

- `codex/visual-style-a`
- `codex/backend-skeleton-maven`
- `codex/unity-prototype-input`

项目经理负责比较实验分支结果，并选择更适合当前阶段目标的方案。

未经用户明确要求，不自动执行以下操作：

- 合并分支。
- 删除分支。
- 推送远程仓库。
- 强制回滚或丢弃已有改动。

## 5. 自治决策边界

项目经理可以直接决定并执行：

- 文档新增与更新。
- 低风险目录创建。
- 概念图素材目录和命名规范。
- 首批概念素材生成。
- 准备低风险本地提交；实际提交前仍需用户验收确认。
- 多角色智能体只读调研、方案比较、计划文档和需求文档任务分派。
- 基于官方文档和可靠资料的技术预研。

项目经理应谨慎处理并记录原因：

- 多模块工程初始化。
- 构建工具选择。
- 协议字段设计。
- 配置表字段设计。
- Unity 工程结构创建。
- 角色尺寸、碰撞范围、技能前后摇等会影响服务端协议的参数。

即使用户授权自治，仍不自动执行：

- 删除、覆盖或回滚用户已有改动。
- 写入或提交密钥。
- 推送远程仓库。
- 合并到 `main`。
- 执行破坏性 git 操作。

## 6. 工作节奏

### 6.1 常规推进

1. 项目经理检查 git 状态。
2. 项目经理读取 `task_plan.md`、`progress.md` 和 `findings.md`。
3. 项目经理拆分任务。
4. 独立的只读调研、方案比较、计划文档或需求文档任务交给对应角色智能体。
5. 项目经理在等待期间处理不冲突的本地工作。
6. 各角色返回后，项目经理整合成果；如需修改代码或项目文件，只能由主线程执行。
7. 更新项目记忆文件。
8. 运行必要检查。
9. 用户验收确认后，按范围创建本地提交。

### 6.2 方案比较

当出现多个可行方案时，项目经理需要记录：

- 每个方案的核心做法。
- 优点。
- 缺点或风险。
- 适用场景。
- 修改范围。
- 测试或检查影响。
- 推荐方案与不推荐其他方案的原因。

### 6.3 素材生成

首批视觉素材先以概念图为主，不直接当作 Unity 最终资源。

素材生成后需要记录：

- 文件名。
- 用途。
- 生成方式。
- 提示词摘要。
- 是否可继续拆成 Unity 资源。
- 质量评价与后续调整点。

## 7. 当前角色智能体状态

当前可启用以下并行只读角色：

- 美术总监：规划首批概念图清单、美术关键词、提示词、素材用途和评审标准。
- 架构师：评估下一阶段推进顺序、边界设计和前后端耦合风险。
- 后端高级工程师：预研后端多模块骨架、最小链路和测试策略。
- Unity 前端工程师：规划 Unity 2D 原型、资源规格和表现验证方式。

这些角色只产出分析和文档。项目经理等待这些角色返回后，会汇总为下一阶段执行方案；涉及代码或项目文件修改时，由主线程智能体统一实施。
